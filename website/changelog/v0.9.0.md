Welcome to Excalibur 0.9! This release enhances the confidentiality and integrity of your data stored on Excalibur servers. Here are the highlights:

- **Encrypted Names**: Excalibur 0.9 does away with the old "obfuscated names" system, replacing it with a proper encryption algorithm to ensure the confidentiality of the names of your stored files.
- **Enhanced Vault Integrity**: Excalibur 0.9 implements a Merkle tree verification system to ensure that, if any data was tampered with while stored on the server, it can be quickly identified and alerted to the user.
- **Reduced Network Traffic**: Enhancements to the server API means that we can send fewer requests to the server to accomplish the same things.

The Excalibur documentation website was also updated in this release with these new changes, as well as reference documentation on the underlying processes involved and server API documentation on how to interact with these new systems.

Do note that there are several breaking changes to Excalibur in this version. Please follow [the 0.9 upgrade guide](/docs/guide/upgrading/08x-to-09x) to upgrade your Excalibur instance to version 0.9. Do also take note of all the breaking changes made to the server API if you are using it.

Read all about the changes to Excalibur below. Enjoy!

## Server

### 💥 Breaking Changes

- 💥 Changed the server to store encrypted item names instead of plaintext ones. The server no longer sees item names.

    Each item now has an encrypted name (`name_enc`) and a name tag (`name_tag`), both produced by the client. The server treats them as opaque bytes. The tag is a keyed hash of the item's parent ID and name, which lets the server enforce that two items in the same folder do not share a name. As a result,
    - Item IDs are now chosen by the client, since the encrypted name needs to contain the ID. The server rejects an ID that already exists with a `409`.
    - `POST /api/files/mkdir/{parent_id}` now takes `{ "id", "name_enc", "name_tag" }` as its body instead of a bare name.
    - `POST /api/files/upload/{parent_id}/{item_details}` replaced the file name with `item_details`, which is `id:name_enc:name_tag` (the ID in its canonical string form, and the other two as URL-safe Base64), end-to-end encrypted like the other path parameters. A malformed `item_details` is a `400`.
    - `POST /api/files/rename/{item_id}` takes `{ "name_enc", "name_tag" }` as its body, and `POST /api/files/rename-multiple` maps item IDs to such objects.
    - `POST /api/files/move/{item_id}` takes `{ "dest_id", "name_tag" }` as its body (previously the destination ID alone), since the tag depends on the parent. Moving a directory into itself or one of its subdirectories is now rejected with a `412`.
    - `POST /api/files/check/names` takes `{ "parent_id", "name_tags" }` as its body and checks the tags.
    - The server no longer rejects names with `/` or file names without `.exef`, and no longer sends a `filename` when downloading a file.
    - The file and directory objects returned by the `/api/files/list`, `/api/files/all` and `/api/files/subtree` endpoints now have a `parent_id`, `name_enc` and (legacy) `name`, and no longer have a `fullpath`.
    - The `/api/files/listen` websocket now sends the ID of the folder that changed (`.` for the root folder) instead of its path.
    - The `name` fields of `/api/merkle/dirty` and `/api/merkle/proof` entries are now optional, and are accompanied by `name_enc`.
    - Removed the `/api/files/search` endpoint, since the server can no longer search names.

- 💥 Made the file CRUD endpoints refer to items by their IDs instead of their paths. In particular, the following endpoints were changed:
    - `HEAD /api/files/check/path/{path}` → `HEAD /api/files/check/item/{item_id}`
    - `POST /api/files/check/paths` → `POST /api/files/check/names`
        - This endpoint now also needs a `parent_id` in the body
    - `HEAD /api/files/check/dir/{path}` → `HEAD /api/files/check/dir/{folder_id}`
    - `GET /api/files/list/{path}` → `GET /api/files/list/{folder_id}`
    - `POST /api/files/mkdir/{path}` → `POST /api/files/mkdir/{parent_id}`
    - `POST /api/files/upload/{path}` → `POST /api/files/upload/{parent_id}/{item_details}`
        - See the encrypted names fragment for the format of `item_details`
    - `GET /api/files/download/{path}` → `GET /api/files/download/{file_id}`
    - `DELETE /api/files/delete/{path}` → `DELETE /api/files/delete/{item_id}`
    - `POST /api/files/rename/{path}` → `POST /api/files/rename/{item_id}`
    - `POST /api/files/move/{path}` → `POST /api/files/move/{item_id}`
        - `new_location` is now a folder ID

- 💥 Removed the file searching endpoint (`/api/files/search`)
- 💥 Updated the OPAQUE authentication response to include the maximum encrypted name size

### ✨ New Features

- ✨ Added endpoints to allow the migration of plaintext item names to encrypted names ([#342](https://github.com/PhotonicGluon/Excalibur/pull/342)):
    - `/api/files/names/pending`: check for (`HEAD`) or list (`GET`) the items that still have a plaintext name
    - `/api/files/names/fill`: submit a chunk of encrypted names, which erases the plaintext names of those items and marks them as dirty for the Merkle tree

- ✨ Added Merkle tree verification of vault data, improving security and data integrity ([#203](https://github.com/PhotonicGluon/Excalibur/pull/203))

    A whole slew of endpoints have been added to support Merkle tree verification:
    - `/api/merkle/dirty`: get the dirty (unverified) items of the current user
        - `/api/merkle/dirty/{item_id}`: check if the given item is dirty (unverified)
    - `/api/merkle/attestation`: get the latest attestation for the current user
    - `/api/merkle/attestations`: get the attestation chain for the current user
    - `/api/merkle/content-mac-inputs`: get the inputs for the content message authentication code (MAC) for the given items
    - `/api/merkle/migrate`: begin migration of a vault to Merkle tree verification
        - `/api/merkle/migrate/fill`: submits a chunk of Merkle data for an in-progress migration
        - `/api/merkle/migrate/complete`: completes an in-progress migration
    - `/api/merkle/mutate`: applies the provided mutation to the Merkle tree
    - `/api/merkle/proof/{item_id}`: gets the inclusion proof for the item
    - `/api/merkle/state`: gets the current vault state

    For more information about how to use these endpoints, please consult the documentation.

- ✨ Added a new subtree endpoint (`/api/files/subtree/{folder_id}`) to list all items within the subtree rooted at the specified folder
- ✨ Added a new endpoint (`/api/files/check/names`) to check the existence of multiple names in a folder at once
- ✨ Added a new endpoint (`/api/files/rename-multiple`) to rename multiple items at once
